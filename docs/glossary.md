# 용어집

카드 혜택과 이 프로젝트 코드에서 자주 나오는 말을 모았습니다. 괄호 안은 코드에서 쓰는 이름입니다.

## 카드 혜택

| 용어 | 뜻 |
| --- | --- |
| 전월 실적 (`prevSpend`) | 이번 달 혜택 크기를 정하는 지난 실적 창(아래 "실적 창")에서 그 카드로 결제한 금액 합계(`monthSpend`). 신용·체크 카드 결제만 세고(`isCardExpense`: 수입·현금·계좌이체·환불 행 제외), 창 안에 들어온 환불은 빼며, 0원 아래로 내려가지 않는다. 상품권·세금처럼 실적에서 빠지는 업종(`spendExcludes`)은 더하지 않는다. 사용자가 고친 값(실적 보정)이 있으면 계산값 대신 그 값을 쓴다 |
| 실적 보정 (`spendTierOverride`, `spendTierOverrideYm`) | 카드 상세에서 사용자가 직접 고친 전월 실적. `spendTierOverrideYm` 달(혜택을 받는 달)의 계산에만 쓴다. 이 달 값이 없는 예전 데이터는 모든 달에 적용된다(`spendOverrideOf`) |
| 실적 구간 (`SpendTier`) | 전월 실적을 나누는 구간. `{ min: 300000, max: 500000 }`은 "30만 원 이상 50만 원 미만". `max: null`은 상한 없음 |
| 실적 창 (`spendWindow`) | 실적을 세는 날짜 범위. `spendWindow(ym, N)`은 ym월에 끝나는 창이다. 청구 사이클 시작일 N(`statementCycleDay`)이 없으면 ym월 1일~말일, 있으면 전월 N일~ym월 N−1일. 전월 실적은 `spendWindow(전월, N)`으로 센다. 그래서 혜택 받는 달 기준으로 기본은 지난달 1일~말일, 사이클이 있으면 전전월 N일~전월 N−1일이다. 예: N=13이면 10월 혜택의 실적 창은 8/13~9/12. 화면에서 고를 수 있는 N은 `CYCLE_DAYS` = 5·10·13·15·20·25. 자세히는 [04. 혜택 계산 엔진](04-benefit-engine.md) 3장 |
| 혜택 규칙 (`BenefitRule`) | 약관 한 조항을 계산할 수 있게 옮긴 것. 대상(업종·가맹점·요일·시간대…), 지급 방식(정률·구간별 정률·정액·금액당·리터당), 한도를 담는다 |
| 정률 (`rate`) | 결제액의 몇 %. `0.1` = 10% |
| 구간별 정률 (`rateBands`) | 결제 한 건의 금액에 따라 비율이 달라짐. 3만 원 미만 0.5%, 3~10만 원 0.7% … |
| 정액 (`fixedAmount`) | 조건을 만족하면 고정 금액. "주말 음식점 2만 원 이상이면 1천 포인트" |
| 금액당 (`step`) | "2만 원당 1천 포인트"처럼 일정 금액마다 |
| 리터당 (`perUnit`) | 주유 "리터당 60원" |
| 대상 금액 상한 (`eligibleAmountCap`) | 혜택 계산에 넣는 결제액의 상한. "1회 승인금액 5만 원까지" |
| 건당 한도 (`perTxnCap`) | 결제 한 건에서 받을 수 있는 혜택의 상한 |
| 월 한도 (`monthlyCap`) | 한 달에 받을 수 있는 혜택 합계의 상한. 실적 구간마다 다를 수 있다 |
| 횟수 한도 (`dailyCount`, `monthlyCount`, `yearlyCount`) | 하루·한 달·한 해에 적용받을 수 있는 횟수 |
| 통합 한도 (`capGroupId`) | 여러 규칙이 월 한도 하나를 같이 쓰는 것. "편의점·병원·세탁소 합쳐서 월 1만 원" |
| 통합 횟수 (`countGroupId`) | 여러 규칙이 일·월·연 횟수를 함께 쓰는 것. 금액 한도 묶음(`capGroupId`)과 별개다. 예: 신한 Point Plan의 "음식점·배달앱 통합 일 1회" |
| 구간별 한도 (`limitsByTier`) | 규칙이 적용되는 실적 구간과 그 구간의 월 한도·횟수 목록. 카드의 지금 구간에 맞는 행이 없으면 "전월 실적 … 구간에는 혜택 없음"으로 막힌다 |
| 월 특례 (`monthOverrides`) | 특정 달에 한도를 늘려 주는 것. "5월·12월은 1만 포인트 추가" |
| 중복 허용 / 배타 (`stacking`) | 한 결제에 두 규칙이 함께 적용되는지. 배타면 큰 쪽 하나만 |
| 원장 (`Ledger`) | 이번 달에 쓴 혜택 금액과 적용 횟수를 쌓아 두는 장부. 금액(`used`)은 `카드:통합 한도 그룹(없으면 규칙 id)`별로, 횟수(`counts`)는 `카드:통합 횟수 그룹(없으면 규칙 id)`별로 센다. 결제를 시간순으로 넣으며 늘려 가고, 남은 한도 = 월 한도 − 사용액. 연 횟수(`year`)는 같은 해 1월~전월 누적을 이어받는다(`priorYearCounts`) |
| 받은 혜택 (`received`) | 실제로 결제한 카드에서 받은 혜택 합 |
| 받을 수 있었던 혜택 (`could`) | 결제마다 보유 카드 중 가장 유리한 카드를 썼다면 받았을 합. 한도를 나눠 쓰는 것까지 고려해 그리디로 배분한 근사값. 받은 혜택보다 작아지지 않게 맞춘다(`could = max(could, received)`) |
| 놓친 혜택 (`missed`) | 한 달 합계. 받을 수 있었던 혜택 − 받은 혜택(그리디 근사) |
| 결제별 차액 (`diff`) | 그 결제를 최적 카드로 했을 때 더 받았을 금액(최적 카드 혜택 − 내 카드 혜택, 0 이상). 앞선 실제 결제가 쓴 한도·횟수를 반영한다. 알림(1,000원 이상 상위 3건), 홈·리포트의 놓친 결제 목록(`missedTop`), 카드별 통계, 엑셀 내보내기에 쓴다. 결제마다 따로 비교하므로 모두 더해도 월간 `missed`와 다를 수 있다 |
| 최적 카드 (`bestCardId`) | 그 결제 시점의 실제 남은 한도 기준으로 가장 많이 주는 카드. 후보는 현재 보유 카드뿐이고, 해제한 카드는 뺀다 |
| 패키지 (`variants`) | 같은 카드 안에서 고르는 혜택 묶음. 삼성 taptap O의 "스타벅스+오픈마켓" / "커피+배달" |
| 정성 혜택 (`Perk`) | 라운지·바우처·우대금리·연회비 면제처럼 결제마다 금액으로 셈하지 않는 혜택. 계산 규칙이 아니라 카드에 딸린 정보라 금액 계산(엔진)에는 들어가지 않는다. 대신 거래 상세에서 AI(`/api/judge`, `PerkJudge`)가 결제마다 받을 가능성(확률)과 형태(돈 / 상품·이용권 / 서비스·자격)를 판단한다(`PerkJudgment`). 자세히는 [06. 정성 혜택 판단](06-perks-jev.md) |
| 계산 불가 규칙 (`supported: false`) | 약관을 아직 확인하지 못했거나 스키마로 표현할 수 없는 규칙. 정성 혜택과 다르다 |
| 조건 필드 (`CondField`) | 영수증만으로는 알 수 없어 사용자가 더 알려 줘야 하는 정보: 결제 시각, 자동납부 여부, 간편결제 수단, 결제 경로(앱/현장/웹), 주유량 |
| 청구할인 / 적립 / 캐시백 (`kind`) | 할인은 청구 금액에서 빼 줌, 적립은 포인트로 줌, 캐시백은 돈으로 돌려줌. 계산 방식은 같고 표시만 다르다 |

## 거래·가계부

| 용어 | 뜻 |
| --- | --- |
| 카테고리 (`categoryId`) | 사용자가 정하는 지출·수입 분류. 상위(식비)와 하위(카페) 2단계 |
| 업종 (`merchantIndustry`, `Industry`) | 혜택 매칭에 쓰는 가맹점 종류(카페, 대형마트, 주유소…). 카테고리와 별개로, 사용자가 카테고리를 바꿔도 혜택 계산은 그대로다 |
| 업종 분류 3단계 (`resolveIndustry`) | 경로마다 순서가 다르다. 영수증: ① 사용자가 예전에 고친 기록 → ② AI가 영수증에서 읽은 업종 → ③ 가맹점 이름 사전. 직접 입력: ① 사용자 기록 → ② 사전 → 없으면 0.7초 뒤 `/api/classify`(서버에서 사전, 그다음 LLM에 가맹점 이름만 보냄). 사용자 기록이나 AI 답이 "기타"(`etc`)면 쓰지 않고 다음 단계로 넘어간다. 사용자 기록은 이 기기의 localStorage에만 있다. 업종이 저장되지 않은 거래는 엔진이 계산할 때 사전으로 채운다(`industryOf`) |
| 업종 미분류 (`isUnclassified`) | 업종을 모르거나 "기타"(`etc`)인 카드 결제. 환불·수입·현금·계좌이체는 세지 않는다. 월간 요약의 "업종 미분류 N건"과 거래 목록 `?unclassified=1` 필터가 이 기준을 쓴다 |
| 환불 (`originalTxnId`) | 원래 결제를 가리키는 지출 거래. 금액은 양수로 저장하고 집계에서 뺀다. 부분 취소도 같다. 어느 달에서 빼는지는 둘로 갈린다. 가계부 집계와 전월 실적은 환불한 날이 속한 달(실적 창)에서 빼고 원결제 달은 바꾸지 않는다. 혜택 계산은 원결제 금액에서 환불 합계를 뺀 유효 금액(`effectiveAmount`)으로 원결제 달을 다시 계산한다. 예: 8/25 결제 10만 원, 9/3 환불 4만 원이면 8월 실적은 10만 원 그대로, 9월 실적은 0원(음수 대신 0)이고, 8월 그 결제의 혜택은 6만 원 기준으로 다시 계산된다 |
| 할부 (`installmentMonths`) | 할부 개월 수. 금액은 총액으로 기록한다 |
| 반복 거래 (`RecurringRule`) | 매월·매주 자동으로 생기는 거래(구독료, 월세) |
| 원화 환산액 (`amountKrw`, `krw()`) | 외화 결제의 원화 금액. 앱은 결제일 환율을 가져오지 않는다. 사용자가 카드 명세서의 원화 청구액을 넣고, 값이 없으면 `krw()`가 고정 대략 환율(`FX_APPROX`: USD 1,380원, JPY 9.2원)로 계산해 "참고값"으로 표시한다. 영수증 화면은 이 대략 환율 값을 미리 채워 두고 고치게 한다. 모든 집계·실적·혜택은 `krw()` 값으로 센다 |
| BIN (`bin`) | 카드번호 앞 6자리. 카드사·상품을 식별하는 번호라 영수증의 카드번호 앞자리와 맞춰 결제 카드를 확정한다. 뒷자리는 받지도 저장하지도 않는다 |
| 데모 모드 / 로그인 모드 | 로그인하지 않으면 빈 장부(기본 카테고리 + 총예산 150만 원)로 시작해 이 브라우저(localStorage)에만 저장되고(공용 데모 계정이 설정돼 있으면 그 계정의 DB), 로그인하면 Supabase DB에 저장된다. 로그인해도 업종 기억(업종 분류 ① 사용자 기록)과 알림 읽음 표시는 이 기기의 localStorage에만 남는다. "오늘"은 두 모드 모두 실제 오늘이다 |
| 참고값 | 실제 청구 금액과 다를 수 있다는 표시. 약관을 옮긴 규칙으로 계산한 혜택 금액, 대략 환율로 바꾼 원화 환산액, AI가 판단한 정성 혜택 확률에 붙는다 |

## 카드 등록·관리자

| 용어 | 뜻 |
| --- | --- |
| 직접 추가 카드 (`custom_…`, `owner_id`) | 기본 카드 목록에 없어 사용자가 입력한 카드. id가 `custom_`으로 시작한다(`isCustomCardId`). 혜택은 "전 가맹점 정률" 규칙 하나이고, 월 한도와 전월 실적 조건은 선택이다. 검수 없이 계산한다(`reviewStatus: "none"`, `customCardProduct`). 데모에서는 localStorage에, 로그인하면 `card_products`에 `owner_id` = 본인으로 저장된다 |
| 관리자 (`app_metadata.role = 'admin'`) | Supabase 로그인 토큰(JWT)의 `app_metadata.role`이 `admin`인 사용자. 카드·규칙·가맹점 사전에 쓸 수 있고, 로그인 모드에서 `/api/normalize`(약관 원문을 규칙으로 바꾸는 AI)를 부를 수 있다 |
| 검수 상태 (`reviewStatus`) | 카드 규칙을 관리자가 확인했는지. `approved` 검수 완료, `pending` 검수 대기, `none` 검수 대상 아님(직접 추가 카드) |
| 카드 등급 (`grade`) | 카드 혜택 구조의 난이도 A~D(`GRADE_DESC`). A 무실적·무한도 정률, B 단일 실적 + 단일 월 한도, C 실적 구간별 한도·요일·시간대, D 통합 한도 매트릭스·구간별 적립률·중복·배타 |

## 기술

| 용어 | 뜻 |
| --- | --- |
| App Router | Next.js에서 `src/app/폴더/page.tsx`가 곧 화면 주소가 되는 방식. 괄호로 감싼 폴더(`(app)`)는 레이아웃을 묶는 라우트 그룹이라 주소에 나타나지 않는다. 예: `src/app/(app)/home/page.tsx` → `/home` |
| Route Handler | `src/app/api/…/route.ts`. 서버에서만 도는 API. AI 키를 브라우저에 노출하지 않으려고 여기서 OpenAI를 부른다 |
| RLS (Row Level Security) | Postgres가 행마다 "이 사용자가 읽고 쓸 수 있나"를 검사하는 기능. 장부 테이블(거래·보유 카드·카테고리·반복 거래·예산·영수증·알림)은 본인 행만 보이게 한다. 카드 상품은 기본 카드(`owner_id` 없음)는 모두 읽고, 직접 추가 카드는 `owner_id` 본인만 읽고 쓴다. 혜택 규칙은 승인된 것(`status = 'approved'`)만 읽힌다(관리자는 모두). 카드·규칙·가맹점 사전 쓰기는 관리자만 할 수 있다. 정책은 `supabase/schema.sql`, 자세히는 [07. 데이터 모델](07-data-model.md) |
| 낙관적 업데이트 | 화면을 먼저 바꾸고 DB 저장은 뒤에서 하는 방식. DB 쓰기는 한 줄로 세워 순서대로 보낸다. 하나라도 실패하면 메시지(`syncError`)를 띄우고, 남은 쓰기가 끝난 뒤 DB 상태를 다시 읽어 화면을 되돌린다 |
| 구조화 출력 (Structured Outputs) | AI에게 JSON 스키마를 주고 그 모양으로만 답하게 하는 기능. 영수증 인식이 항상 같은 필드를 돌려받는 이유 |
| 디자인 토큰 | 색·글꼴 크기·둥글기 같은 값을 이름(`--color-primary`, `text-label`)으로 정해 두고 그 이름만 쓰는 것 |
